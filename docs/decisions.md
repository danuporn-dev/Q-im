# Decisions

ค่าเริ่มต้นที่เลือกแทนตามคำสั่งเจ้าของโปรเจกต์ (2026-11-25) เปลี่ยนได้ภายหลัง รายการที่เจ้าของโปรเจกต์กำหนดเองมีเครื่องหมาย **(กำหนดแล้ว)**

| # | เรื่อง | ค่าที่ใช้ |
|---|---|---|
| D01 | `shops.capacity` **(กำหนดแล้ว)** | จำนวนออเดอร์ที่ทำพร้อมกันได้ ใช้คำนวณ ETA เท่านั้น |
| D02 | `max_active_orders` **(กำหนดแล้ว)** | เพดานปฏิเสธ checkout นับ `PENDING + ACCEPTED + PREPARING`; ว่าง = ไม่จำกัด |
| D03 | `business_date` **(กำหนดแล้ว)** | ตัดรอบเที่ยงคืน Asia/Bangkok ยึดเวลาที่ร้านยืนยัน |
| D04 | `admin_accounts` แยก **(กำหนดแล้ว)** | session แยก cookie ตาม realm: customer / merchant / admin และสิทธิ์จริงคือ realm ตัดกับ `user_roles` |
| D05 | `public_order_no` | `QI` + yymmdd (วันที่สั่ง เวลาไทย) + `-` + 6 ตัวสุ่มที่ไม่มีอักษรกำกวม |
| D06 | `shop_members.permissions` | `NULL` = สมาชิกทุกคนของร้านมีสิทธิ์เท่ากัน ยังไม่แบ่งย่อย |
| D07 | การอนุมัติร้าน | Admin เป็นผู้สร้างร้าน `active = 0` คือยังไม่อนุมัติ/ถูกปิด ไม่มีสถานะแยก |
| D08 | `PENDING` ที่ร้านไม่ตอบ | ไม่หมดอายุอัตโนมัติ ลูกค้ายกเลิกเองได้ และ dashboard ร้านเตือนเมื่อรอเกิน 5 นาที |
| D09 | `REFUNDED` | ไม่มี workflow คืนเงินใน MVP ยืนยันชำระได้เฉพาะ `READY` และ `READY` ที่ `PAID` ยกเลิกไม่ได้ จึงไม่มีออเดอร์ที่จ่ายแล้วถูกยกเลิก |
| D10 | LINE secrets | `LINE_CHANNEL_SECRET` และ `LINE_CHANNEL_ACCESS_TOKEN` เป็นของ Messaging API; ฝั่ง Login ใช้เพียง `LINE_LOGIN_CHANNEL_ID` เพื่อ verify ID token |
| D11 | ยืนยันตัวตอนรับ (แก้ตาม D31/D32) | ร้านสแกน QR บนมือถือลูกค้า ซึ่งเป็นเลขออเดอร์เต็ม หรือพิมพ์เลขเต็ม; API ฝั่งร้านปิด 4 ตัวท้าย; ผิดครบ 5 ครั้งต่อออเดอร์ล็อกการสแกน ต้องส่งมอบพร้อมเหตุผล (D27) ซึ่งถูกบันทึก |
| D12 | ETA (แก้ตาม D32) | งานของออเดอร์ = เวลาเมนูที่นานที่สุด + 1 นาทีต่อชิ้นที่เพิ่ม; เมนูที่ไม่มีเวลาใช้ค่าเฉลี่ยจริง 14 วัน (ตั้งแต่ 5 ออเดอร์, วัดจาก `cooking_started_at` ถึง `ready_at`) หรือค่าที่ร้านตั้ง; ออเดอร์ที่ได้ช่องทำอาหารแล้ว ETA = งานของตน − เวลาที่ทำไปแล้ว (ต่ำสุด 1); ยังไม่ได้ช่อง ETA = ceil(งานค้างก่อนหน้า / capacity) + งานของตน; ไม่มี capacity หรือข้อมูลไม่พอ = ประเมินไม่ได้ |
| D13 | เวลาเปิดปิด | ไม่มีแถว `shop_hours` = รับได้ทุกเวลา; `close < open` = ข้ามเที่ยงคืน; ต้อง `accepting_orders = 1` ด้วย |
| D14 | ราคาเปลี่ยนระหว่าง checkout | client ส่ง `quote` (hash ของราคา) ถ้าไม่ตรงตอบ 409 `PRICE_CHANGED` และให้ยืนยันใหม่ |
| D15 | ขีดจำกัดข้อมูลเข้า | ตะกร้าไม่เกิน 30 รายการ จำนวน 1–20 ต่อรายการ หมายเหตุ 255 ตัวอักษร |
| D16 | ยอดขายในรายงาน | ผลรวม `payments.status = PAID` ตาม `paid_at` ของช่วงวันที่เวลาไทย |
| D17 | การแจ้งเตือน | แจ้งเมื่อรับ ปฏิเสธ พร้อมรับ และร้านยกเลิก; ลองสูงสุด 5 ครั้ง; งานเก่ากว่า 24 ชั่วโมงไม่ส่ง |
| D18 | ยอมรับข้อเสนอหัวข้อ 17 ของ CLAUDE.md | ใช้ตามที่เสนอทั้งหมด |
| D19 | การทดสอบ **(กำหนดแล้ว)** | `tests/run.php` และ `scripts/e2e.php` ใช้ `qim_test` เท่านั้น สร้างจาก migrations + seed และลบเอง ไม่เขียน `qim_dev` |
| D20 | Migration | เขียนให้ใช้ได้ทั้ง MariaDB 10.4+ และ MySQL 8.0.16+ แต่ทดสอบจริงเฉพาะ MariaDB |
| D21 | เปลี่ยนร้านในตะกร้า | API ตอบ 409 `CART_SHOP_CONFLICT` จนกว่า client ส่ง `replace: true` หลังผู้ใช้ยืนยัน |
| D22 | Git | commit ต่อ phase ที่ branch `feature/mvp` ไม่ push |
| D23 | Rate limit **(กำหนดแล้ว)** | ลูกค้าที่ login แล้วนับตาม user id; login ร้าน/ผู้ดูแลนับบัญชี + IP; เพดานอยู่ใน deploy.md |
| D24 | ถอด role ลูกค้า | ได้ role อัตโนมัติเฉพาะครั้งแรกที่สร้างผู้ใช้ Admin ถอดแล้ว login ใหม่ไม่ได้คืน |
| D25 | ชื่อลูกค้า | API ฝั่งร้านไม่ส่งชื่อลูกค้า ตามที่แจ้งใน privacy notice |
| D26 | READY no-show **(กำหนดแล้ว)** | ร้านยกเลิก `READY` ที่ `UNPAID` ได้เมื่อพร้อมรับครบ `READY_ALERT_MINUTES` (ค่าเริ่มต้น 20 ใช้ร่วมกับตัวเตือน ตั้งระดับระบบใน `.env` เพื่อไม่ให้ร้านลดเวลาเอง ค่าที่ไม่ถูกต้องใช้ 20) ต้องมีเหตุผล; audit `order.no_show`; ไม่ auto-cancel |
| D27 | ส่งมอบโดยไม่ใช้รหัส **(กำหนดแล้ว)** | ร้านทำเองพร้อมเหตุผล ไม่ต้องให้ admin อนุมัติ; audit `pickup.override` filter ได้ที่ `GET /admin/audit-logs?action=pickup.override`; หน้า admin แสดงจำนวนสะสมต่อร้านแบบอ่านอย่างเดียว |
| D28 | การสาธิต **(กำหนดแล้ว)** | `demo-reset.php` = reset `qim_dev` + `seed-demo.php` (แทน `seed.php`); ป้าย, login แตะเดียว, แชทจำลอง และ placeholder SVG ใช้ได้เฉพาะ `APP_ENV=development`; `POLL_SECONDS` (2–60) ใช้ได้ทุก environment ว่าง = ค่าเดิม 6–10 วินาที |
| D29 | ข้อมูลออเดอร์ที่ลูกค้าเห็น | allow-list ใน `Orders::forCustomer`; `reason` ส่งเฉพาะ `REJECTED`/`CANCELLED` (รวม no-show) เหตุผลการส่งมอบโดยไม่สแกน QR เห็นเฉพาะร้านและผู้ดูแล |
| D30 | สาธิตผ่านอินเทอร์เน็ต **(กำหนดแล้ว)** | `DEMO_ACCESS_CODE` (เฉพาะ development; นับเฉพาะรหัสผิด 20 ครั้ง/15 นาที/IP), `DEMO_PUBLIC` ค่าที่ไม่ชัดเจนถือว่าเปิด, `TRUSTED_PROXY` เชื่อ `X-Forwarded-*` ค่าสุดท้ายจาก IP ที่ระบุตรงตัวเท่านั้น; VirtualHost ต้องมี allow-list |
| D31 | ร้านทำงาน 3 ขั้น + ส่งมอบด้วย QR **(กำหนดแล้ว)** | **รับออเดอร์** = `accept` พา `PENDING → ACCEPTED → PREPARING` ใน transaction เดียว (ออกคิว, log ทั้งสองสถานะ, แจ้ง `ORDER_ACCEPTED` ครั้งเดียว); **อาหารพร้อม** = `ready` (รับจาก `ACCEPTED` ของออเดอร์เก่าได้ โดยผ่าน `PREPARING`); **ส่งมอบ** = `complete` พร้อม `pickup_qr` + `payment_received: true` ยืนยันเงินและปิดออเดอร์ในขั้นเดียว (audit `payment.confirm` ยังบันทึก) ไม่ส่ง `payment_received` แล้วยังไม่จ่าย = 409 `PAYMENT_REQUIRED`; QR ของลูกค้าคือเลขออเดอร์เต็ม ร้านเห็นแบบปิด 4 ตัวท้าย ผิด = 422 `PICKUP_QR_WRONG`; ไม่มี `pickup_code` แล้ว; ร้านสแกนด้วยกล้อง (`BarcodeDetector` หรือ jsQR), รูปถ่าย, เครื่องสแกน หรือพิมพ์เลขออเดอร์เต็ม; สแกนไม่ได้ใช้เหตุผล (D27) ได้เหมือนเดิม; ETA นับคิวก่อนหน้าตามลำดับ FIFO และ capacity แทนสถานะ เพราะทุกออเดอร์ที่รับแล้วเป็น `PREPARING`; endpoint `prepare` และ `payment` ยังอยู่เพื่อความเข้ากันได้ แต่หน้าร้านไม่ใช้ |
| D32 | ช่องทำอาหาร, ยืนยันรับเงิน, จำกัด QR ผิด **(กำหนดแล้ว)** | `fillKitchen` ให้ช่อง (capacity) แก่ออเดอร์ที่รับแล้วตามลำดับคิว เมื่อรับ/พร้อม/ยกเลิก/เปลี่ยน capacity บันทึกใน `orders.cooking_started_at` (migration 009, ข้อมูลเก่าใช้ `preparing_at`); `complete` ตรวจ QR ก่อนเงิน ถ้ายังไม่จ่ายตอบ 409 `PAYMENT_REQUIRED` แล้วหน้าร้านแสดงยอดกับปุ่ม "ได้รับเงินแล้ว" ซึ่งส่ง `payment_received: true` เฉพาะเมื่อร้านกด; QR/เลขผิดนับใน `orders.pickup_failures` และ audit `pickup.qr_wrong` (เก็บเลขครั้ง ไม่เก็บค่าที่สแกน) ครบ 5 ตอบ 409 `PICKUP_QR_LOCKED`; `accept` กับออเดอร์ที่ `ACCEPTED` หรือ `PREPARING` อยู่แล้วตอบ 200 ไม่เปลี่ยนอะไร |
| D33 | แผนงานปรับเรื่องเวลา **(กำหนดแล้ว)** | เป็นการตัดสินใจเรื่องเวลา ไม่ใช่ข้อบกพร่อง: เทสต์เต็มชุด + e2e รันแค่หลัง A0 และตอนจบ (ระหว่างทางรัน `php -l` + เทสต์ส่วนที่แตะ; A6 รัน T22 และเทสต์ชำระเงิน/ส่งมอบทั้งหมดก่อน commit); **A5 (จอทีวี `/display/`, display token) เลื่อนไปทำทีหลัง**; A4 ทำ endpoint ตัวเลข และ `demo-history.php` ครบ ส่วนกราฟเป็นตารางหรือแท่ง CSS อย่างง่าย; A0, A6 และรีวิวความปลอดภัยตอนจบทำครบทุกข้อ |
